# Pitfalls

Reviewed through: PR #97 (2026-10-19) · next ID: P26

Check every diff against **All changes**, then against each section it touches.

## All changes

- **P8 · Docs follow the interface.** `docs/integrations.md`, the READMEs, `deploy/README.md`, runbooks, the specs and plans a settled decision amends, config examples and test comments match the changed behaviour; a documented command runs as written, from the directory it names, with every argument and prerequisite. Check: grep the docs for every name, rule and decision you changed, and run each command you documented.
- **P19 · A test fails when the behaviour breaks.** Reverting the fix turns it red; it drives the production caller, not the helper below it; fixtures follow the API contract and reflect their own writes; it waits on durable state or polled readiness, never timing or sleep; a smoke or acceptance check requires the page's own success marker or the exact condition claimed; a prerequisite the test's own setup guarantees (a seeded paper, a stack page) fails instead of skipping, while an optional local one (`TEST_DATABASE_URL`) still skips. Check: for each new test, what broken code would still pass it?
- **P12 · Edge inputs keep their meaning.** `0`, `false`, empty and unknown are values: no `x or None`, bare truthiness, unknown read as zero, absent written as `""` or a zero metric dropped; parsers reject impossible values (Feb 31, month 13) and accept every valid form, including the one litwatch writes itself; formatting keeps the value (`{:g}` truncates epochs); structured text parses nested brackets and wrapped lines; values compare as structures, not substrings; TeX matching strips `%` comments first, minding `\%` and backslash parity. Check: grep the diff for `or None`, `?? 0`, `|| ""`, `:g`, truthiness on optional values, and ID, date and markup patterns.
- **P14 · A status says only what is known.** A failed request, an outage or a malformed upstream reply is an error with a retry, never empty content or "not found"; each status (queued, running, failed, terminal, draft) renders as itself, alike on every surface; status copy and health promise no retry, progress or cause that was not observed; a health check fails on overdue work and stays degraded until evidence clears it; a failure that happens is recorded where the owner will see it. Check: make each dependency fail and step through every status. Does each surface say only what the data proves?
- **P4 · One rule decides membership, scope, filters and topic status.** Parents count their descendants; keyword, uncertain and held paths count; paused, draft and unfollowed topics and dismissed papers get their specified treatment in every action, alert, count, cache and UI choice; every view and every search tier of one selection applies the same normalization, filters, order and colours; SQL, `core` and the web agree, and the web takes eligibility and validation from the API instead of restating them. Check: does the new query, tier or component restate a rule that `core` or another surface already has, and what does it do with each topic status and a dismissed paper?
- **P9 · Explicit configuration wins, and empty is not absent.** An explicit disable beats environment credentials; an empty section is not a disabled one; an optional feature or fallback needs no settings while unused, never takes the primary's routing, and fails inside its own work; dates use the configured timezone, across its DST changes, not the browser's or the runner's. Check: try the feature off, empty, env-only and missing its dependency, and run it in another timezone across a DST change.
- **P11 · Touch only what this run owns.** Tests run under `env -i` with only `TEST_DATABASE_URL` and what they need, so no exported shell variable reaches production or host services, and a test that drives the CLI first changes to a temporary directory, since every command loads `./.env`; a sandbox copy drops cluster-local positions (outbox XIDs, cursors) and live external job references (batches, Deep jobs); a scratch guard resolves the database it connected to, not the DSN's text; a delete checks that this invocation created its target, by a marker it left, not a name or filename pattern, comparing the database name after PostgreSQL truncates it or the normalized path; a signal re-identifies its process (start time, working directory) when sent; logs stay until the process is confirmed dead. Check: if its environment were the shell's, which production database, service, job, file or process could this test, sandbox, eval or script reach, and what is the worst existing thing a delete or signal could match?
- **P24 · A write whose reply is lost can be retried.** An external create, batch submission or owner action that committed before its reply was lost is found again on retry, by an idempotency key or by adopting what exists, and the retry returns the state the client needs to reconcile. Check: kill the caller after the remote side commits and before it records. Does the retry duplicate the work, or leave the client stuck?

## Backend

- **P1 · Recovery and retry follow current policy, not fresh-work rules.** Retries, lost leases, sweeps, restarts and owner run-now see current state but no fresh-work cap, keep the original deadline and routing, read results already available before paying again, advance monotonically and skip what is known to fail (a refused model, a terminal 404 or NotFound), and validate a recovered answer like a fresh one; every caller that can find the work recovers it; retry intent is stored, not inferred. Check: walk each queue through retry, lost lease, restart, sweep and owner takeover. Does each reach the work exactly once?
- **P2 · Combined data belongs to one paper revision.** A verdict, Weight or Gist joined to a paper is from its current revision; an older Brief or Deep card is kept only as the spec allows, labelled with its revision; a frozen record (digest, eval run, Calibrate session, miss trace) reads only what it froze, and an explanation once given (a Why, a cause) is stored, not recomputed; reuse, resume and reconciliation keys hold the revision, every input that changes the answer (title, abstract, model, fallback list) and the target they belong to. Check: in each join, key and reuse, what happens if the paper, the configuration or the target changed in between?
- **P5 · Bounds cover the whole invocation.** `--limit`, caps, budgets, deadlines, leases, timeouts and concurrency limits apply in SQL before loading, across every phase, fallback and retry path, and around the whole operation rather than each read or each item; a size limit measures the bytes sent; a part's timeout fits its caller's budget; a guard that cannot check fails closed. Check: can a loop, a later phase, a fallback, a retry, a serial sum of timeouts or a trickling HTTP body get past the bound?
- **P10 · Usage counts every billed attempt.** Costs and run counts come from each attempt as it happens, killed, refused, retried and failed ones included, durably before the call, grouped by the configuration that ran and attributed by ID; an unknown charge stays unknown (a lower bound, never $0); an estimate averages only calls billed the same way; a failing cleanup neither skips cost collection nor replaces the job's error. Check: does an interrupted, refused or fallen-back attempt still show in the totals, and how is an unknown cost printed?
- **P20 · A report claims only what its data shows.** Every number traces to a committed export; a rerun never overwrites the evidence a report cites, and an eval never mutates the baseline it reads; the baseline comes from the source the report names; acceptance criteria are fixed before the results; a comparison changes one thing at a time; run-to-run variation is measured before it is invoked. Check: for each claim in the report, which committed file proves it?
- **P3 · Check and act under one lock, and hold no lock across I/O.** An eligibility read and the write it permits share one transaction holding the locks, taxonomy first and then papers; archive, arXiv and model calls run outside it, and the write after them rechecks and tolerates a concurrent insert. Check: what can a dismissal, rewrite, pause or concurrent worker change between your check and your write, and is a lock held while you wait on the network?
- **P7 · A change settles what depends on it, in the same transaction.** A rewrite, class move, topic reorder, eligibility or configuration change re-derives grades, rarity, library, PDF policy, passes and what integrations exported, and writes its outbox event atomically; a compound owner action (fetch then report, fetch then Deep request) commits once, and nested helpers neither commit nor settle inside it; nothing points at data (a `current` link, a handed-out batch ID) before that data is durable. Check: what derived state reads the thing you changed, and what is left if the action fails halfway?
- **P21 · Code that runs in parallel shares nothing unsafe, and ends before what it uses.** Each task in a `gather`, `TaskGroup` or `to_thread` has its own connection; a library that is not thread-safe runs one call at a time; tasks sharing a budget or lock coordinate through it; when one task fails, its siblings are cancelled and awaited before the lock, journal or client they use is released. Check: for each new concurrent path, list what the tasks share, and follow one task's failure to the cleanup.

## Web

- **P16 · Navigation keeps the reader's place.** Back restores the list snapshot, scroll, focus and history entry; a refetch never reorders what is on screen, and an item that arrives later takes a stable place; a refresh never remounts rows with open controls; steps, redirects and in-page moves push or replace history as the spec says; an in-page jump opens what hides its target first; drafts and acknowledgements are keyed by their item, revision and failure episode, so they neither leak to the next nor vanish on refresh, and a pristine draft adopts refreshed data. Check: open, edit, step, refresh, leave and come back, on phone and desktop. Does everything land where it was?
- **P17 · A write refreshes every view that reads what it changed.** Each mutation invalidates or patches every representation (lists, counts, summary, strips, digests, sidebars), in both directions of a transition, after success and after a conflict; a failed refetch is not taken as fresh data; an invalidation restarts the reads it cancels; a run or pass is polled through every pending state, and its terminal status is read together with the data it vouches for. Check: list the queries that read the changed entity. Does each refresh after success, 409 and failure, and does polling stop only on a terminal state?
- **P15 · A late response or callback never overwrites newer state.** Overlapping writes apply in order; a read begun before a write or a run's completion cannot restore what came after it; pending clears only after the refresh lands; a mutation's reply patches only the rows the server says it changed; timers, pointer sessions and settle callbacks end with their owner (close, navigation, unmount), and a durable effect does not depend on a mounted component. Check: for each mutation and async callback, what if an older read lands after it, or the reader leaves before it finishes?
- **P18 · Controls stay whole at every width.** Every phone control keeps a 40 px target; rows wrap or drop whole items instead of clipping, at phone width and in fixed desktop rails; flex children holding controls do not shrink; a padding change does not push a label past its container's threshold. Check: render the changed screens at 360 px and at the narrowest desktop rail. Is anything clipped, squeezed or under 40 px?
- **P23 · A change to something shared stays where it was meant.** CSS for one page is scoped to it, so a global class (`.fchip`, `.tag`, `.srow`) does not restyle another page; a shared component (`Prose`) gains behaviour only for the consumer that asked for it. Check: grep for every class and component you changed. Which other pages use them, and do they still look and behave the same?

## Watching

- Gesture recognizers take input that belongs to editing, a nested scroller, another recognizer, or native pan and zoom (PR #73).
- ARIA roles promise keyboard behaviour that is not built; hidden controls stay in the tab order (PR #70).
- Model-output validation checks against more than the prompt supplied, or strips markup that hides wording it should check (PR #93).
- An integration finds remote items by a mutable title or a mere mention of their ID, takes the wrong item kind, or edits what the owner made (PR #76, #77, #92).
