## How it ran

From this worktree (no `.env` here), one CLI process per step. Each step ran after `.env.v1`, with
`LITWATCH_DATABASE_URL` pointing at `n6_restart` and only the two API keys taken from `.env`, as
`env -u ANTHROPIC_BASE_URL uv run litwatch …`. The database started empty: migrations and the seed taxonomy only.
Configuration is `config.py`'s defaults (schedule off, no integrations, so Zotero is off), except step 5's file.

| Step | Command | Archive in its environment | Cap (running total) |
| --- | --- | --- | --- |
| 1. Intake | `litwatch intake archive --since 2026-10-09 --until 2026-10-15` | the live archive, its listing read only; no archive integration, so nothing registered | |
| 2. Classification, analysis, grading | `litwatch nightly --no-fetch --no-digests` | none, so the full-text passes queue and wait | $11 |
| 3. Full-text passes | `litwatch fulltext --wait 7200` | the disposable archive on 8798 | $58 |
| 4. Digests | `litwatch digests write --since 2026-10-12 --until 2026-10-18` | the disposable archive | $62 |
| 5. Deep cards | `litwatch fulltext --deep --config evals/2026-10-16-restart/deep.toml --wait …` | the disposable archive | subscription |
| 6. JIT timing | `uv run python evals/2026-10-16-restart/jit.py --repeats 7 --out evals/2026-10-16-restart` | none | |

- **The window.** No seven days of submissions make whole listing days, since arXiv's cutoff is 14:00 ET. Monday
  10-12 lacks the share submitted Thursday 10-08 after the cutoff. Friday 10-16 holds only the share of 10-15
  submitted before the cutoff.
- **The cap.** `2026-10-16-restart/cap.sh n6_restart CAP PID` ran beside each paying step. Every 10 s it sums the
  journal's cost over every role and provider, and once the sum reaches CAP it stops the step's process by PID,
  after checking that it is still the same process run from this checkout. It is a watchdog, not an admission
  check: the calls answered since the last sum and those in flight at the stop are paid past CAP, up to about $3.70
  for the passes (eight at up to $0.46) while the sums succeed. Three failed sums in a row stop the step too, after
  up to two minutes unwatched. The cap was never reached. The run used the earlier `cap.sh`, which lacked the
  failed-sum stop and the same-process check, both added after review.
- **Step 2 writes no digests.** `nightly` ends with today's digests over every paper announced in the 21 days before
  today, so one daily would have taken the whole window. `--no-digests`, added for this run, leaves out the wait and
  those digests; step 4 writes the window's.
- **Step 3 comes before the digests,** as on a night: an Area must read is a pick candidate only once its Weight
  re-check has finished. The Area must reads queue their re-checks at the volume the owner accepted on 2026-10-15,
  untuned.
- **Deep (step 5)** runs after the digests, since Area picks exist only once their digests are published.
  `litwatch serve --port 8796`, with no configuration and a run read token, served `store.search` to the dev deep
  instance. That instance ran from `deep/` on 8797, with `DEEP_AUTH_FILE=/srv/appdata/litwatch-v1-dev/deep/auth.json`.
  `deep.toml`, read only by this step, held `max_per_day = 24` for the run (the owner's word of 2026-10-16). It went
  back to 10 in the commit that records the run; nothing shared changed.
- **Stopping.** Serve and deep were stopped by the PID that owns their port (`ss -H -ltnp 'sport = :8797'`), after
  checking its `/proc/<pid>/cwd`. `$!` from `nohup node …` names a wrapper, and the listening process outlives it.
