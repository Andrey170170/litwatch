# The restart (milestone N6), draft

Draft of 2026-10-16, branch `feat/restart`. Phase 1 holds the plan, a slice measured to estimate the cost, and the
JIT timing queries; the run itself waits for the owner's approval of its cost. Tooling is in `2026-10-16-restart/`.
After the slice, `n6_restart` was dropped and made again: migrated, the seed taxonomy, nothing else, so the run starts
at step 1.

## The run

**What it tests.** That v1 builds a readable collection from nothing (build plan V9; decision 48): the two most
recent weeks read from the archive and run through the whole pipeline, unlabelled. The check is the counts and cost
per step against the estimates, every Focus paper at central with its Brief or the reason it has none, and the digests
of the window written. It runs on the scratch database `n6_restart` on `litwatch-v1-dev`, created empty, with the
migrations and the seed taxonomy (`litwatch taxonomy import`) and nothing else.

**How it runs.** On the host, by the CLI, one step at a time, from this worktree (no `.env` here). Each command runs
after `.env.v1` with `LITWATCH_DATABASE_URL` set to `n6_restart` and only the two API keys taken from `.env`, as
`env -u ANTHROPIC_BASE_URL uv run litwatch …`. Not the compose stack: it brings its own Postgres and archive, and one
process per step lets the cap and the archive differ by step; the stack smoke test already covers the stack.
Configuration is `config.py`'s defaults (schedule off, no integrations), except the Deep step's file. Zotero is off,
since no library integration is configured.

| Step | Command | Archive in its environment |
| --- | --- | --- |
| 1. Intake | `litwatch intake archive --since S --until U`, the 14 submission days ending the day before the run (2026-10-02 to 10-15 for a run on 10-16: 6,255 papers) | the live archive, read only: its paper listing |
| 2. Classification, analysis, grading | `litwatch nightly --no-fetch --no-digests` | none, so the full-text passes are queued and wait |
| 3. Full-text passes (Briefs, Weight re-checks) | `litwatch fulltext --wait 3600` | the disposable archive |
| 4. Digests | `litwatch digests write --since <first listing day> --until <the Sunday after the last>` (2026-10-05 to 10-18), so both weeks get their weeklies | the disposable archive |
| 5. Deep cards | `litwatch fulltext --deep --config evals/2026-10-16-restart/deep.toml --wait …` | the disposable archive |
| 6. JIT timing | `uv run python evals/2026-10-16-restart/jit.py` | none |

- **The archives.** The live archive's URL and token are set only for step 1's command. Intake reads the listing and
  registers nothing, since there's no archive integration section. From step 3 on, `LITWATCH_ARCHIVE_URL` and
  `LITWATCH_ARCHIVE_TOKEN` are the disposable archive's (`scripts/disposable-archive.sh start 8798`). Its worker
  fetches each pass's source from arXiv at urgent priority, so every registration and urgent fetch lands there.
- **The volume accepted on 2026-10-15.** The Area must reads queue their Weight re-checks at the volume the owner
  accepted (a median of 20 a night for Alignment and safety, 12 for Interpretability), with no tuning first. Step 3
  works the queue before the digests, so an Area must read is a pick candidate only once its re-check has finished,
  as on a night.
- **Step 2 writes no digests.** `nightly` ends with today's digests, over every paper announced in the 21 days
  before today, so on a weekday one daily digest would take the whole window, and on a Monday the week before's
  weekly would come ahead of its dailies. `--no-digests` leaves out the wait and those digests; step 4 writes the
  window's.
- **Deep cards.** Step 5 comes after the digests because Area picks exist only once their digests are published.
  `litwatch serve --port 8796` serves the read API that deep's `store.search` asks; it runs with no configuration, so
  no worker, scheduler or dispatcher starts. A run read token is set for it. The dev deep instance runs from
  `deep/` on port 8797, with `DEEP_AUTH_FILE=/srv/appdata/litwatch-v1-dev/deep/auth.json` and `LITWATCH_URL` and
  `LITWATCH_TOKEN` pointing at that serve. A card takes up to 30 minutes, one at a time.
- **Deep's daily limit is one setting.** `2026-10-16-restart/deep.toml`, the run's own file and read only by step 5,
  holds `[integrations.deep]` with the URL and `max_per_day = 24`: the owner's word of 2026-10-16 for the full run,
  so 30–60 cards take two to three days. No shared configuration changes (`deploy/litwatch.toml`, `config.py`'s
  defaults): everything else keeps 10. After the run, the file goes back to `max_per_day = 10`, in the commit that
  records the run.
- **Ports.** 8796 (serve), 8797 (deep), 8798 (the disposable archive). 8791–8793 are left alone. Serve and deep
  are stopped by the PID that owns their port (`ss -H -ltnp 'sport = :8797'`), after checking its `/proc/<pid>/cwd`:
  `$!` from `nohup node …` names a wrapper, and the listening process outlives it.

**The spending cap.** `2026-10-16-restart/cap.sh n6_restart CAP PID` runs beside each step. Every 10 s it sums the
call journal's cost in `n6_restart`, which covers every role and provider and accumulates across steps. Once the sum
reaches CAP it stops the step's process by PID, after checking the process runs from this checkout. Calls in flight
at the stop are paid but not yet journalled, so the overshoot is at most a step's concurrency times its dearest call:
about $1.40 for four full-text passes, cents elsewhere. Each step gets its own cap, set from the projection below.
OpenRouter's key usage is read before and after as a check on the journal; the deep service spends its subscription,
not the API, and each attempt records its usage.

- **The main agent's projection is low by about a third.** Its $17 for the pipeline holds ($17–18). Its $55–60 for

- **The confounders.** One weekday, not a Monday (a Monday folds in a weekend: twice the papers, same rates); five

$170 on 2026-10-15) covers it.

## JIT timing

`2026-10-16-restart/jit.py` records the statements the reading API issues and runs each under
`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` with `jit` on and off, back to back, the order alternating between repeats.
The lists are Papers as a whole and at each depth, and every shown topic's page, each its counts, its page and its
rows. It prints the median execution time summed per list on and off, the JIT time, and how many statements JIT
compiled, and keeps every plan in `plans.jsonl.gz`. The dev server is PostgreSQL 17.10 with `jit = on` and
`jit_above_cost = 100000`, so JIT compiles a statement only when its estimated cost exceeds that. Tried on the slice's
541 papers: 4.5–15 ms a list, no statement compiled, so the slice says nothing about JIT; it runs on the restart's
6,255 after step 5.
